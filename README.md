1. Start Docker Desktop, install Ollama, `ollama pull qwen3:4b-instruct-2507-q4_K_M`   (Qwen3-4B-Instruct-2507, 4-bit; pinned, not the moving tag `qwen3:4b-instruct`)
2. `ollama create qwen3-4b-instruct-16k -f Modelfile`   (= qwen3 instruct with 16k context)
3. `python -m venv .venv` and activate, `pip install -r requirements.txt`
4. `docker build -t agai-sandbox sandbox/`
5. `python tools/get_data.py`
6. `python tools/smoke_test.py`  -> exit 0, `(33076, 40)` and the trace (setup check only: Ollama -> Docker -> data; runs in a temporary folder, nothing is kept)

Docker Desktop and Ollama must both be running for every experiment.

## Experiments: condition -> run -> seed
Every result belongs to a **condition** (WHAT is tested: one step and one change, e.g. `B4_strong`) and to one
**run** of it (WHO ran it, WHEN, on WHICH machine, e.g. `vanessa_1`). Every run uses the same 5 **seeds**; one seed is
one **case**, and a case holds one folder per **version** of the code (`v1` = baseline, `2a`/`2b`/`2c` = reflection).

```
experiments/
  B4_strong/                 condition: B = baseline step (Step 1), R = reflection step (Step 2)
    condition.json           fixed conditions: level, base condition, model, temperature, prompt hashes, shims
    prompts/                 copy of every prompt exactly as it was used
    vanessa_1/               run: <person>_<n> (person from the machine, config.RUNNERS)
      run.json               person, machine, model digest, git commit/dirty, base run, seeds, status
      s101/
        trace.jsonl          one line per action (llm, exec, result), with version and stage
        v1/                  response.md  code.py  notebook.ipynb  stdout.txt  stderr.txt  result.json (our evaluation)
          outputs/           what the model's code saved: *.png, results.json (its answer)
    jan_1/                   a repetition of the same condition by Jan
  R2_2b/
    vanessa_1/               base run: B4_strong/vanessa_1 (reflects on exactly these frozen v1s)
      s101/2b/               + feedback.md (what the critic saw)  critique.md
  _legacy/                   old series E01-E21 and the first runs L00-L09 (flat: experiment.json + cases/)
results/                     generated by analyze.py, can be rebuilt any time
```

Rules:
- **The condition id is chosen by hand and stays fixed.** Running it with a changed prompt, model, temperature,
  schema or shims is refused, whoever runs it: use a new id.
- **Runs are named by the machine.** `config.RUNNERS` maps the machine name to a person; an unknown machine stops
  with a message (or set `AGAI_PERSON` for one session). The same command again resumes *your* unfinished run;
  a further run of a condition you already finished needs `--repeat` (`mischa_1` -> `mischa_2`).
- **Reflection builds on one base run and never regenerates v1.** It loads the frozen v1 of that run, so baseline,
  2a, 2b and 2c of a seed all start from exactly the same code. (The same seed does not reproduce a long answer,
  not even on the same machine; see logbook entry 11. So `s101` of two runs are two different cases.)
- **Results are averaged in two stages**: first over the 5 seeds of a run, then over the runs of a condition
  (`PERFORMANCE_LOG.md`, section 0). A reflection condition is compared with its base **run by run** (paired).

## Workflow
Every change to the setup is one version with an entry in [`docs/changes.md`](docs/changes.md) (hypothesis, expected and measured effect).
```
# Step 1: baseline (one generate per seed)
python step1_baseline.py --exp <id> --prompt step1_baseline_v1 --schema --seeds 101-105 --change "what is different"
python step1_baseline.py --exp <id> --prompt step1_baseline_v1 --seeds 101-105          # lower bound, no schema

# The series B1-B4 / R1-R3 (one option added per condition, each justified by the previous run's errors; see docs/changes.md)
python step1_baseline.py --exp B1_original_prompt --prompt step1_baseline_v1 --seeds 101-105 --change "..."
python step1_baseline.py --exp B2_schema --prompt step1_baseline_v1 --schema --seeds 101-105 --change "..."
python step1_baseline.py --exp B3_shims --prompt step1_baseline_v1 --schema --shims --seeds 101-105 --change "..."
python step1_baseline.py --exp B4_strong --prompt step1_baseline_v2 --schema --shims --seeds 101-105 --change "..."

# Repeat a condition (same command + --repeat; --change only for a new condition): B4_strong/jan_1, mischa_1, ...
python step1_baseline.py --exp B4_strong --prompt step1_baseline_v2 --schema --shims --seeds 101-105 --repeat

# Old baseline (comparison point): notebook prompt, the model saves results.json itself
python step1_baseline.py --exp <new_id> --schema --prompt legacy/step1_baseline_v3 --shims --seeds 101-105 --change "..."

# Step 2: reflection levels on the frozen v1 of ONE baseline run (shims are inherited from the base)
python step2_reflection.py --exp R1_2a --level 2a --base B4_strong/vanessa_1 --change "B4 + reflection 2a"
python step2_reflection.py --exp R1_2a --level 2a --base B4_strong/jan_1 --repeat   # the same condition on Jan's B4 run
# (--base B4_strong is enough while B4_strong has a single run)

# Analysis: results/versions.csv + results/comparison_<base run>.html (seed x level, transitions, cost)
python analyze.py                                   # also rebuilds PERFORMANCE_LOG.md
python analyze.py --base B4_strong/vanessa_1
python analyze.py --trace B4_strong/vanessa_1 101   # one trace as a story (--full: with prompts and answers)
python analyze.py --run B4_strong/vanessa_1 101     # all details of one version (--details: one line per version)
# Wherever an id is asked for, a condition with a single run is enough (B4_strong); old experiments by their id (E10_baseline_v3)
```

What the critic sees per level (`src/feedback.py`):

| Level | In addition to its own code |
|---|---|
| 2a | nothing |
| 2b | exit code, stdout, traceback, plain run observations (run time, size of the output, sentences printed, RESULTS_JSON line printed or not, number of plots), a text description of every saved plot |
| 2c | 2b + independent check of each RESULTS_JSON value (supported / refuted / missing) and of what the report text claims (months, busiest month, strong flares, trend: supported / refuted); never the correct value. A missing RESULTS_JSON line is named explicitly |

Naming: condition `<letter><n>_<change>` (B = baseline step, R = reflection step; later T tools, P planning,
M multi-agent), run `<person>_<n>`. The old series is `E<nn>_<level>_<...>` in `experiments/_legacy/`.
Reading a case: open `experiments/<condition>/<run>/s<seed>/` – `trace.jsonl` for the full history,
the version folders for code, output, plots and `result.json`.

## Code
| File | Purpose |
|---|---|
| `config.py` | model, temperature, limits, paths, `RUNNERS` (machine -> person) |
| `src/experiment.py` | condition (`condition.json`) and run (`run.json`), resume and `--repeat`, `resolve`/`load` of a run id |
| `src/trace.py` | `Case` (one seed) and `Version` (one code version), the trace of a case |
| `src/llm.py` | Ollama call with a hard wall-clock limit (`LLM_MAX_SECONDS`), seed passed through |
| `src/evaluate.py` | one evaluation for every step: checker facts, error category, funnel, report quality (5 dimensions), cost, `notebook.ipynb` |
| `src/feedback.py` | what the critic sees per reflection level |
| `src/checker.py` | compares RESULTS_JSON with `ground_truth.json` |
| `src/schema.py` | neutral data schema for the prompt |
| `src/runner.py` | executes code in the Docker sandbox, plots go to the version's `outputs/`; contains the runner helpers (`SHIM`: `display`, numpy-safe `json.dumps`) |
| `analyze.py` | CSV, two-stage means per condition, comparison tables, `PERFORMANCE_LOG.md`, `--trace`, judges and human scores |

Tests (no Ollama or Docker needed): `python tests/test_<name>.py`, e.g. `python tests/test_step2.py`.

## Reading the results (traces, funnel, routine)

With the below listed files one can check on **how the model performs, what changed, and what resulted after the change**:

| File | What it is | Who writes it |
|---|---|---|
| `PERFORMANCE_LOG.md` | section 0: one row per condition (mean over runs); then one row per run: what changed, funnel, facts, cost, conditions | generated by `python analyze.py` |
| `notebooks/EDA_Report.ipynb` | example solution, **for looking at only**: what a good answer to the research question looks like. Nothing is measured against it; only `ground_truth.json` and the error table count | created with an AI model, checked against `ground_truth.json` |
| `experiments/<condition>/<run>/` | the raw evidence (code, output, traces) behind every row of the log | written by the step scripts |

### 1. Words you will meet

| Word | Meaning |
|---|---|
| **condition** | WHAT is tested: one fixed set of conditions (model, temperature, prompt, schema, shims), e.g. `B4_strong` |
| **run** | one execution of a condition by one person on one machine, with 5 seeds, e.g. `B4_strong/vanessa_1`. A repetition of the condition is another run (`jan_1`, `mischa_2`) |
| **seed** | a number handed to the model's random sampler; `s101` is "repetition 101" inside a run. A reflection run and its base run share the same frozen `v1` of a seed, so `s101` of B4 and `s101` of R2 (on that B4 run) are paired. Across runs they are not: long answers are *not* reproducible with the same seed (logbook entry 11) |
| **case** | one seed inside one run: `experiments/B4_strong/vanessa_1/s101/` |
| **two-stage mean** | mean over the 5 seeds of each run, then mean of the run means (`PERFORMANCE_LOG.md` section 0); **sd runs** = spread between runs, **sd seeds** = spread inside a run |
| **version** | one piece of code inside a case: `v1` = first answer of the model, `2a`/`2b`/`2c` = revised after reflection |
| **frozen v1** | reflection never regenerates `v1`; it starts from the stored one, so baseline and reflection are compared on the same code |
| **ground truth** | facts computed from the CSV with plain pandas (`ground_truth.json`, built by `step0/facts.py`); the model's numbers are compared with it |
| **funnel** | the stages a run has to pass one after the other (section 4) |

### 2. The five-minute routine after every experiment

```
python analyze.py                                   # rebuilds PERFORMANCE_LOG.md, results/versions.csv, results/comparison_*.html
open PERFORMANCE_LOG.md                             # 0. per condition, 1. per run: did depth / facts move? 2. Funnel: where do runs stop?
python analyze.py --trace B4_strong/vanessa_1 101   # read ONE trace as a story (before forming an opinion)
```

Then, for the seeds that look interesting, open `<run>/s<seed>/v1/`:

| File | Look here to see |
|---|---|
| `response.md` | what the model answered (text around the code) |
| `code.py` | the exact code that was run |
| `stdout.txt` / `stderr.txt` | what the code printed / why it crashed |
| `outputs/*.png` | the plots it saved |
| `outputs/results.json` | **the model's answer** (baseline v3 and later): the 7 values its code computed and saved. Not checked, may be wrong |
| `notebook.ipynb` | the generated code as a notebook (only if the model used the `# %%` format; code only, no outputs) |
| `result.json` | **our evaluation** of the run, written by `src/evaluate.py`: exit code, error category, funnel, which of the model's values are correct (`checks`, `fact_score`), report quality, cost |
| `feedback.md`, `critique.md` (levels 2a-2c only) | what the critic was shown and what it answered |

`outputs/results.json` and `result.json` are two different files with similar names. Everything in `outputs/` was
produced by the model's code inside the sandbox (plots and its answer). Everything directly in the version folder was
written by us (the extracted code, the captured output, the evaluation). `result.json` grades the content of
`outputs/results.json` (or, before baseline v3, of the `RESULTS_JSON` line in `stdout.txt`).

### 3. Reading a trace: a real example (E01, seed 101, old series in `_legacy`)

`python analyze.py --trace E01_baseline_schema 101` prints:

```
  1  16:13:09  v1  version_start start (parent: -)
  2  16:19:53  v1  llm           generate: 1347 tokens in, 1508 out, 403.72s, finish=stop
  3  16:20:00  v1  exec          code code.py: exit=1, 7.28s  | TypeError: Object of type int64 is not JSON serializable
  4  16:20:00  v1  result        result: exit=1 error=json_serialize ...
```

Read it like a sentence: *the version started; the model was asked once (1,347 tokens in, 1,508 out, 404 s) and stopped
normally; the code was run and crashed after 7 s with a JSON error; the evaluation recorded the category `json_serialize`.*

What each event tells you:

- **`llm`**: cost (tokens, seconds) and `finish`. `stop` is normal; `length` means the answer was cut off at `MAX_TOKENS`;
  `wall_timeout` means the model took longer than `LLM_MAX_SECONDS`. Add `--full` to see the prompt and the answer.
- **`exec`**: `exit=0` means the code finished. Anything else is a crash; the last line of stderr is shown.
- **`result`**: the verdict of the evaluation, the same numbers that end up in the log.

Where did the crash happen? `result.json` has `error_line` (here 123). The script has 123 lines, so it computed
everything and failed in its very last line, the `json.dumps`, because `numpy.int64` is not JSON-serialisable. The same trace shows
a second problem that the crash hides: the report text in `code.py` is typed in as a fixed string
("busiest month being February 2021") *before* anything was computed. Always open `code.py` too, the trace alone does not
show that.

### 4. The funnel: how far did a run get?

A run passes the stages in order. **Depth** = number of stages passed in a row (0-8).

| # | Stage | Passes when | If it fails, look at |
|---|---|---|---|
| 1 | `answered` | the model returned an answer | trace `error` event (timeout, Ollama down) |
| 2 | `code_found` | the answer contains a ```python block | `response.md` |
| 3 | `ran` | exit code 0 | `stderr.txt`, `error_category` in `result.json` |
| 4 | `json_found` | a `RESULTS_JSON:` line is printed | `stdout.txt` (did the script reach the end?) |
| 5 | `json_strict` | that line is valid JSON | `stdout.txt` (Python dict with single quotes, `np.int64(...)`) |
| 6 | `keys_complete` | all 7 requested keys are present | `stdout.txt` |
| 7 | `any_fact` | at least one value matches the ground truth | `checks` in `result.json` |
| 8 | `all_facts` | all 7 values match | `checks` in `result.json` |

Why not only `facts`? A crash in the last line and a crash in line 5 both give 0 % facts. Depth separates them, and
**Crash at** in the log (position of the error line in the script, 100 % = last line) shows how close a crashing run came.

**Facts from the text.** If a run prints no `RESULTS_JSON` line, the JSON-based `facts` are blind (0 % because nothing could be read,
not because the analysis is wrong). `PERFORMANCE_LOG.md` section 4b therefore also shows the facts that can be read from the report
text (months, busiest month and its count, number of strong flares, trend) as `right / readable`. This is an extra measure; the
baseline and the funnel are not changed by it.

Things the funnel does *not* measure yet (still open in the evaluation plan): the text of the report (`report_precision` in
`result.json` is a first, rough number) and the subjective quality of plots and report (the LLM judge).

### 5. Starting an experiment

1. Start **Docker Desktop** and **Ollama** (`ollama list` must show `qwen3-4b-instruct-16k`). Your machine must be in
   `config.RUNNERS` (the script tells you if not).
2. A **new condition**: pick a new id and say what is different:
   ```
   python step1_baseline.py --exp <new_id> --prompt step1_baseline_v2 --schema --shims --seeds 101-105 \
       --change "what is different"
   ```
   `--change` is required for a new condition (it becomes the "What changed" column). Running the same command again
   resumes your unfinished run.
3. A **repetition** of an existing condition: the same command with `--repeat` instead of `--change`. For a reflection
   condition, `--base` names the baseline run it reflects on (your own, e.g. `B4_strong/jan_1`).
4. `python analyze.py`, then the routine from section 2.

Credentials / conditions: every condition stores in `condition.json` the model, temperature, shims and a hash of every
prompt; every run stores in `run.json` the person, the machine, the model digest, the Ollama URL, the Docker image and the
git commit (section 7 of the log). There is no API key involved (the key in `src/llm.py` is a dummy for local Ollama).

### 6. Shims: the environment is a condition too

The runner helper `SHIM` (`src/runner.py`) makes the sandbox behave like a notebook (`display` exists, `json.dumps` accepts
numpy numbers). It hides two kinds of model errors, so it is a *condition*: `condition.json` stores `runner_shims` and the
hash of the text, and the log shows `Shims on/off`. Its effect was measured inside the series: B2 -> B3 adds only `--shims`,
and the generated code of all 5 seeds was byte-identical in both runs, so the whole difference comes from the shims
(`docs/changes.md`, row B3).

### 7. "Why did the number change?" checklist

When a row in the log moves, check in this order:

1. **Same conditions?** Section 7 of the log: model digest, temperature, prompt hashes, commit, machine. A different hash means a different condition, not noise; a different digest or machine between runs of one condition is worth a look.
2. **Bigger than the spread?** The log shows `mean ± sd` over the seeds, and section 0 the spread between runs
   (`sd runs`). A change smaller than these is not a result. With one run per condition, `sd runs` is unknown:
   repeat the condition (`--repeat`) before you call a small difference a result.
3. **Which stage moved?** Section 2 of the log: if only `ran` moved, the code got fewer crashes; if `any_fact` moved, the numbers got better.
4. **Read two traces:** one that got better and one that did not, with `analyze.py --trace ... --full`.
5. **Cost:** tokens and seconds per seed. A gain at 5x the tokens is a different statement than a free gain.
